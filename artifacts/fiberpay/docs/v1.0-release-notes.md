## What is WeaveWallet?

WeaveWallet is a **non-custodial Progressive Web App** that lets you
scan any Lightning invoice — from a Phoenix wallet, an LND admin UI, a
Strike account, a Square terminal — and pay it from your **Fiber
stablecoin balance** (RUSD or USDI), settled atomically by your own
Fiber node. You run the node. We just hold the camera. There is no
custodian to trust, no key derived from your passkey, and no payment
the wallet won't report on honestly.

---

## Key features

- **Scan any bolt11 Lightning QR** with your phone's camera — invoice decoding happens entirely in-browser
- **Pay with stablecoin** (RUSD / USDI) instead of CKB, with live USD-equivalent display and per-asset balance toggling
- **Passkey-gated UI** (Face ID, Touch ID, Windows Hello) via WebAuthn — biometrics confirm intent, but the spending key lives on your node
- **User-node-first architecture** — point WeaveWallet at any Fiber node you control via JSON-RPC, no central server in the loop
- **Honest settlement reporting** — Fiber and Lightning legs tracked and surfaced independently (Settled / Pending confirmation / Failed / Unverified); the wallet never claims success it hasn't verified
- **PWA installable** on iOS Safari and Android Chrome with a real Add-to-Home-Screen flow, offline indicators, and a service-worker cache
- **Activity export** to CSV (with UTF-8 BOM + formula-injection guard) and JSON for accounting and audit
- **Premium dark UI** with volt-green (#16c953) accents, framer-motion transitions, and haptic feedback on every primary action
- **Comprehensive test coverage** — 67 Vitest tests across business logic, error mapping, exports, Fiber client + mock client, signature-based caching, and offline UX
- **Full deployment + real-world testing docs** including a Docker-Compose-to-Square-Sandbox end-to-end guide

## Current limitations

Be honest about what v1.0 does and does not give you. None of these
are bugs — they're scoped-out decisions or upstream constraints.

- **Self-hosted Fiber node required.** WeaveWallet does not custody funds and does not bundle a node. Real payments need a node you run and fund yourself — see [`deployment-and-testing.md`](./deployment-and-testing.md) for the full setup. A simulated "test mode" is built in for poking around the UI without a node.
- **Lightning fulfillment is your node's guarantee, not the wallet's.** Cross-network atomicity (Fiber leg + Lightning leg settling together) is enforced on the node, not in the PWA. The wallet polls both ledgers and reports what it sees; refund of a failed half-payment is the node's responsibility. See [`lightning-fulfillment.md`](./lightning-fulfillment.md).
- **Testnet-focused for v1.0.** The documented end-to-end flow is verified against Fiber testnet + Square Sandbox. Mainnet works the same way technically, but no automated mainnet stress testing has been performed. Re-run the entire guide on mainnet from scratch before pointing real money at it; don't promote a testnet config by flipping a flag.
- **Bolt11 only.** The scanner accepts raw bolt11 invoices (with or without the `lightning:` prefix). LNURL-pay payloads, on-chain BTC addresses, and BIP21 URIs are rejected with a clear error. If your merchant only exposes LNURL, use an intermediary wallet to resolve it to a bolt11 first.
- **Single-payment flow only.** v1.0 ships scan-and-pay. Receiving payments into the Fiber node, channel management, on-chain operations, and multi-party splits are intentionally out of scope and live in the node's CLI / admin UI.
- **No telemetry.** Zero analytics, zero error reporting, zero phone-home. Privacy by default — but it also means we can't see your bug unless you tell us about it.
- **RPC method names tracked best-effort** against public Fiber documentation. Operators on bleeding-edge node builds may need to verify `node_info`, `list_channels`, `new_invoice`, `send_payment`, `get_payment`, `get_lightning_invoice`, and `lookup_invoice` against their version. See `artifacts/fiberpay/src/lib/fiber/real-client.ts`.

## How to get started

### Just kick the tires (5 minutes, no node required)

```bash
git clone https://github.com/your-org/weavewallet.git
cd weavewallet
pnpm install
pnpm --filter @workspace/fiberpay run dev
```

Open the URL printed in the console. The wallet boots in **test mode**
with simulated balances and simulated payments — fine for exploring
the UI and seeing how failure flows look.

### Pay your first real Lightning invoice (2–4 hours, real node required)

Follow the end-to-end guide:

**→ [Deploy WeaveWallet + Run Your First Real Lightning Payment on Square](./deployment-and-testing.md)**

It walks you from a fresh VPS to a paid Square Sandbox transaction
with copy-paste commands for every step.

### Companion docs

- [Testing checklist](./testing-guide.md) — broader real-world checklist with 8 deliberately-triggered failure cases and a production-readiness gate
- [Fiber node setup](./fiber-node-setup.md) — Docker Compose template + troubleshooting table for the node alone
- [Lightning fulfillment & atomicity](./lightning-fulfillment.md) — how the two-leg payment works and what your node guarantees

### Inside the app

Once you've connected to a real Fiber node, the green **"Ready to test
with real funds?"** banner appears on Home with a one-tap link to the
in-app checklist at `/help`.

## Call for early feedback & pilot testers

WeaveWallet v1.0 is **production-shaped** but **pilot-grade**. We're
specifically looking for:

- **Fiber node operators** willing to run the wallet against their own node and report what works (and what doesn't) on real Fiber builds we haven't tested
- **Merchants** with a Square Sandbox or BTCPay setup who can ring up real Lightning sales and tell us how the scan → pay → confirmation flow feels at a point-of-sale tempo
- **Developers** interested in alternative bridges, additional stablecoin assets, or a desktop/native build — open an issue with what you'd want
- **Designers and accessibility reviewers** — the UI is dark-mode-only and hasn't been audited for screen readers; we'd love patches

**How to send feedback:**

- File issues at the repo (link below) with the `pilot-feedback` label
- For sensitive reports (security, lost funds, node misbehavior), open a **private GitHub Security Advisory** on the repo — do not file them as public issues. A dedicated `SECURITY.md` with a coordinated-disclosure policy is on the v1.1 shortlist.
- Share what you learned publicly — tag any post with `#WeaveWallet` so other operators can find it

Every pilot report shapes v1.1. The faster we learn what breaks in the
wild, the faster we can ship a wallet anyone's family can use.

## What's next (post-v1.0)

Not committing to a roadmap, but the strong candidates for v1.1 are:

- Receiving payments into the node directly from the wallet UI
- Built-in LNURL-pay resolution (so merchants exposing LNURL Just Work)
- A native iOS / Android build for users who can't or won't use a PWA
- Encrypted activity backup + restore across devices
- Multi-language support (currently English-only)
- A `SECURITY.md` and a coordinated disclosure process
