# Deploy WeaveWallet + Run Your First Real Lightning Payment on Square

This is the end-to-end guide for going from a fresh server to ringing
up a real sale on a Square terminal and paying it with stablecoins from
your own Fiber node. Follow it top-to-bottom the first time. Every
command is copy-pasteable.

> **Estimated time: 2–4 hours** for someone comfortable on a Linux
> command line; longer if you're setting up your first VPS or your
> first Fiber channels. Most of the time is waiting for chain
> confirmations.
>
> **Cost: ~$5–$10/month VPS + ~10,000 testnet CKB (free from a
> faucet)** for the testnet run-through. Mainnet costs depend on
> channel sizes.

> *Screenshot placeholders are marked `[SCREENSHOT: ...]` throughout —*
> *swap in real captures from your own run when you ship this guide.*

## 1. Prerequisites

You need all of the following before starting:

### Hardware / hosting
- [ ] A **VPS** running Ubuntu 22.04 or 24.04 LTS with at least:
  - 2 vCPU, 4 GB RAM, 40 GB SSD
  - A public IPv4 address
  - SSH access as a non-root user with `sudo`
  - **Recommended providers**: Hetzner CX22 (~€5/mo), DigitalOcean Basic Droplet ($6/mo), Linode Nanode ($5/mo), or Vultr Cloud Compute ($6/mo). Any of these is plenty.

### Domain & TLS
- [ ] A **domain name** you control (or a free subdomain — DuckDNS, no-ip.com, deSEC are fine for testing)
- [ ] DNS A record pointing the domain at your VPS's public IP
- [ ] Ports **80** and **443** open in your VPS firewall (Caddy needs both for automatic Let's Encrypt)
- [ ] If you're running the **Fiber node on the same VPS** (recommended for this guide): also open the node's peer/gossip ports — **8228/tcp** and **8229/tcp**. The JSON-RPC port (8227) should **not** be exposed to the public internet; the wallet reaches it via the same Caddy reverse proxy on 443.

### Square account
- [ ] A **Square Developer account** with **Sandbox** access — sign up at https://developer.squareup.com
- [ ] At least one **Sandbox Test Location** with **Lightning** payments enabled in the Square Sandbox Dashboard
- [ ] The **Square Point of Sale app** installed on a second device (phone or tablet) and signed in to your Sandbox account
- [ ] *(Optional, only if you want a physical terminal in the loop)* A Square Terminal or Square Register in your Sandbox environment

### Fiber testnet wallet & funds
- [ ] A way to receive **testnet CKB** — the address generated by your Fiber node in step 3 is fine
- [ ] At least **~10,000 testnet CKB** (free from https://faucet.nervos.org/)
- [ ] Access to at least one **Fiber bridge peer** for testnet — see https://fiber.world/ for the current list, or run your own bridge for advanced setups
- [ ] *(Optional)* A small amount of **testnet RUSD or USDI** if you want to seed balances before your first channel rebalance — most testnet bridges will let you swap CKB into stablecoin

### Local tools
- [ ] `git`, `docker`, `docker compose v2`, `make`, `ssh`, `curl` on both your laptop and the VPS

> **Strong recommendation:** do the entire guide on **testnet first**. There is no rollback button for a botched mainnet channel.

## 2. Deploy the wallet on a VPS

### 2.1 SSH in and prepare the host

```bash
ssh youruser@your.vps.example.com

# Install Docker, Docker Compose, make, and git
sudo apt update && sudo apt upgrade -y
sudo apt install -y ca-certificates curl gnupg make git ufw
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
newgrp docker

# Verify
docker --version
docker compose version
```

Lock down the firewall:

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Only if you'll run the Fiber node on this same VPS (section 3):
sudo ufw allow 8228/tcp   # Fiber P2P
sudo ufw allow 8229/tcp   # Fiber gossip
# DO NOT expose 8227 publicly — the wallet reaches it via Caddy on 443.

sudo ufw enable
```

### 2.2 Clone the WeaveWallet repo

```bash
mkdir -p ~/apps && cd ~/apps
git clone https://github.com/your-org/weavewallet.git
cd weavewallet
```

> Replace `your-org/weavewallet` with your actual repo. If you don't
> use git, `scp -r` the project up from your laptop instead.

### 2.3 `docker-compose.yml` for the wallet

Create `~/apps/weavewallet/deploy/docker-compose.yml`:

```yaml
services:
  wallet:
    image: node:24-alpine
    container_name: weavewallet
    restart: unless-stopped
    working_dir: /app
    volumes:
      - ../:/app
    command: sh -c "corepack enable && pnpm install --frozen-lockfile && pnpm --filter @workspace/fiberpay run build && pnpm --filter @workspace/fiberpay run serve --port 4173"
    # `serve` is defined in artifacts/fiberpay/package.json and runs
    # `vite preview --host 0.0.0.0` — don't rename it to `preview`,
    # there is no such script.
    expose:
      - "4173"
    networks:
      - web

  caddy:
    image: caddy:2-alpine
    container_name: weavewallet-caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    networks:
      - web
    depends_on:
      - wallet

networks:
  web:

volumes:
  caddy_data:
  caddy_config:
```

### 2.4 `Caddyfile` (automatic TLS)

Create `~/apps/weavewallet/deploy/Caddyfile`. Replace
`wallet.example.com` with your domain:

```caddy
wallet.example.com {
  encode zstd gzip

  # Security headers
  header {
    Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"
    X-Content-Type-Options "nosniff"
    X-Frame-Options "DENY"
    Referrer-Policy "strict-origin-when-cross-origin"
    Permissions-Policy "camera=(self), microphone=()"
  }

  reverse_proxy wallet:4173
}
```

> **Nginx alternative.** If you prefer nginx + certbot, configure a
> standard reverse proxy to `127.0.0.1:4173` and run
> `certbot --nginx -d wallet.example.com`. Caddy is recommended here
> because TLS is fully automatic with zero config.

### 2.5 `Makefile` for everyday operations

Create `~/apps/weavewallet/deploy/Makefile`:

```makefile
.PHONY: up down restart logs build status

COMPOSE = docker compose -f docker-compose.yml

up:
        $(COMPOSE) up -d

down:
        $(COMPOSE) down

restart:
        $(COMPOSE) restart

logs:
        $(COMPOSE) logs -f --tail=200

build:
        $(COMPOSE) build --no-cache

status:
        $(COMPOSE) ps

update:
        cd .. && git pull
        $(COMPOSE) up -d --force-recreate

shell:
        $(COMPOSE) exec wallet sh

caddy-reload:
        $(COMPOSE) exec caddy caddy reload --config /etc/caddy/Caddyfile
```

### 2.6 Bring it up

```bash
cd ~/apps/weavewallet/deploy
make up
make logs        # Ctrl-C to detach
```

First boot takes 2–5 minutes (pnpm install + build). Watch for:

- `pnpm install` → `Done in Xs`
- `vite v5.x building for production...` → `built in Xs`
- `Local: http://localhost:4173/`
- Caddy: `serving initial configuration` and a Let's Encrypt cert grant

Visit **https://wallet.example.com** from your phone. You should see
the WeaveWallet splash screen with the passkey unlock.

`[SCREENSHOT: WeaveWallet splash on phone, served from your domain over HTTPS]`

### 2.7 Add to home screen

- **iOS Safari**: Share → Add to Home Screen
- **Android Chrome**: tap the install prompt, or three-dot menu → Install app

The wallet now launches like a native app and has camera access.

## 3. Run your own Fiber node

The wallet is non-custodial — it cannot pay anything until you have a
funded node it can talk to. You can run the node on the **same VPS**
or on a separate machine. Same VPS is simpler for first-time setup;
separate machine is better for production isolation.

### 3.1 Use the existing compose template

The repo ships `artifacts/fiberpay/docs/fiber-node-setup.md` with a
complete `docker-compose.yml` for the Fiber node. Don't retype it —
just follow that doc through **sections 2 and 3** to start the
container and write `config/fiber.yaml`.

Quick recap of what you'll do there:

```bash
mkdir -p ~/apps/fiber-node && cd ~/apps/fiber-node
# Drop in the docker-compose.yml from fiber-node-setup.md §2
# Drop in config/fiber.yaml from §3 — IMPORTANT: set a strong rpc.auth_token
docker compose up -d
docker compose logs -f fiber
```

`[SCREENSHOT: docker compose logs showing "JSON-RPC listening on 0.0.0.0:8227" and connected peers]`

### 3.2 Get the node a CKB deposit address

```bash
docker compose exec fiber fnn-cli wallet new-address
# => ckt1q...   (testnet)
```

Copy this address.

### 3.3 Fund it from the testnet faucet

1. Go to https://faucet.nervos.org/
2. Paste the address from step 3.2
3. Request the maximum (typically ~10,000 CKB per day)
4. Wait for ~4 minutes (~24 confirmations)

Verify the funds landed:

```bash
docker compose exec fiber fnn-cli wallet balance
# => available: 10000 CKB (or similar)
```

`[SCREENSHOT: terminal showing non-zero wallet balance]`

### 3.4 Open at least one channel per asset

Pick a bridge peer from https://fiber.world/ (or your own). Then:

```bash
# Open a RUSD channel
docker compose exec fiber fnn-cli channel open \
  --peer 03abc...@1.2.3.4:9735 \
  --funding-amount 5000 \
  --asset RUSD

# Optional: open a USDI channel too
docker compose exec fiber fnn-cli channel open \
  --peer 03abc...@1.2.3.4:9735 \
  --funding-amount 5000 \
  --asset USDI

# Wait a few minutes for confirmations
docker compose exec fiber fnn-cli channel list
```

You're ready for the wallet to connect once at least one channel shows
`state: active`.

`[SCREENSHOT: fnn-cli channel list showing one or more active channels]`

## 4. Connect the wallet to your node

### 4.1 Decide how the wallet reaches the node

#### Same-VPS deployment (recommended for this guide)

Put both compose projects on a **shared Docker network** so Caddy can
reach the Fiber container by its service name. This is the only
deployment pattern documented here because it's the one we've actually
verified works end-to-end.

**Step 1.** On the node host, declare the network as `external` so the
wallet's compose project can join it:

Edit `~/apps/fiber-node/docker-compose.yml` and add at the bottom:

```yaml
networks:
  default:
    name: fiber-net
```

Recreate the node so it joins the new network:

```bash
cd ~/apps/fiber-node
docker compose down
docker compose up -d
```

**Step 2.** Wire the wallet's Caddy container into the same network.
Edit `~/apps/weavewallet/deploy/docker-compose.yml` and replace the
`networks:` block at the bottom with:

```yaml
networks:
  web:
  fiber-net:
    external: true
```

Then add `fiber-net` to the `caddy` service's network list:

```yaml
  caddy:
    # ...everything else unchanged...
    networks:
      - web
      - fiber-net
```

**Step 3.** Add a second Caddy site block for the node RPC.
In `~/apps/weavewallet/deploy/Caddyfile`, append:

```caddy
node.example.com {
  encode zstd gzip
  header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"

  # Hard-restrict who can hit the RPC. Even though it's auth-token
  # gated, narrowing the source IP set is cheap defense-in-depth.
  # Replace 203.0.113.0/24 with the network range your phone uses.
  @trusted {
    remote_ip 203.0.113.0/24
  }
  handle @trusted {
    reverse_proxy fiber:8227
  }
  respond 403
}
```

Apply: `cd ~/apps/weavewallet/deploy && make up && make caddy-reload`.
Caddy now serves the JSON-RPC at **`https://node.example.com`** by
talking to the `fiber` service over the shared `fiber-net` network.

> **Security note.** Even with the auth token from
> [`fiber-node-setup.md` §3](./fiber-node-setup.md#3-configfiberyaml),
> the node's spend RPC should never be wide-open to the internet. The
> `@trusted` block above is the minimum — for production, consider
> mTLS, a WireGuard tunnel between phone and VPS, or a Tailscale
> private endpoint. Do not skip this step.

#### Different machines

If your node lives on a separate box (your laptop, a home server) and
you don't want to expose it at all, use an SSH tunnel for testing:

```bash
ssh -L 8227:localhost:8227 youruser@node.example.com
# In the wallet Settings, use http://localhost:8227 — only works while
# the tunnel is open AND only from the device running the ssh client.
```

For a permanent multi-machine deployment, replicate the Caddy +
`@trusted` pattern above on the node host instead.

### 4.2 Configure the wallet

1. Open **https://wallet.example.com** on your phone.
2. Splash screen → unlock with passkey (first run creates one).
3. Tap the gear icon → **Settings**.
4. **Mode**: switch to **Real node**.
5. **RPC URL**: `https://node.example.com` (or whatever you exposed).
6. **Auth token**: paste the same token you put in `fiber.yaml`.
7. Tap **Test connection**.
   - Expected: green check, your node alias + pubkey within ~3 seconds.
8. Tap **Save**.
9. Back on Home, the status dot turns **green** and the balance card
   shows your real channel capacity.

`[SCREENSHOT: Settings page after a successful connection test]`

If anything is red, jump to [section 7 Troubleshooting](#7-troubleshooting).

### 4.3 Look for the "Ready to test with real funds?" banner

Once you're connected to a real node, the green
**"Ready to test with real funds?"** banner appears on Home. Tap
**Open** to load the in-app `/help` checklist — it mirrors this guide
in a phone-friendly format.

`[SCREENSHOT: Home screen with Ready-to-test banner visible]`

## 5. Fund the node with test stablecoin (RUSD / USDI)

Opening a channel doesn't give you stablecoin balance — it gives you
CKB locked into a Fiber channel that can route stablecoin payments.
You need to **acquire some RUSD or USDI** on testnet to actually spend.

### 5.1 Option A — swap via your bridge peer

Most public Fiber testnet bridges support a `swap` RPC that converts
CKB capacity into stablecoin balance over an open channel:

```bash
docker compose exec fiber fnn-cli swap \
  --from CKB \
  --to RUSD \
  --amount 1000
```

Check balances:

```bash
docker compose exec fiber fnn-cli wallet balance --all
```

You should see a non-zero RUSD entry.

### 5.2 Option B — receive a stablecoin invoice from another testnet wallet

If you have a second Fiber testnet wallet (or a friend does):

```bash
docker compose exec fiber fnn-cli invoice new \
  --amount 1000 \
  --asset RUSD \
  --description "seed"
# => fnp1...  (Fiber invoice string)
```

Send the invoice to the other wallet and have them pay it. Your RUSD
balance goes up.

### 5.3 Verify it shows up in WeaveWallet

Open WeaveWallet → pull to refresh on Home. The balance card should
now show the same RUSD (or USDI) figure as `fnn-cli wallet balance`.

`[SCREENSHOT: Home balance card showing non-zero RUSD or USDI]`

If the balance card stays at $0.00 but the CLI shows funds, see
[7.4 "Wallet shows zero balance but CLI shows funds"](#74-wallet-shows-zero-balance-but-cli-shows-funds).

## 6. End-to-end test with a real Square Lightning QR

This is the real payoff. You will ring up a sale on Square, have it
generate a Lightning bolt11 QR, and pay it with stablecoin from your
Fiber node.

### 6.1 Open Square Point of Sale in Sandbox

1. On your second device, open the **Square Point of Sale** app.
2. Confirm the top-left chip says **"Sandbox"** — if not, sign out and back in with your Sandbox account credentials.

`[SCREENSHOT: Square POS showing Sandbox indicator]`

### 6.2 Ring up a small sale

1. Tap **Library** → choose any item, or tap the keypad and enter a custom amount.
2. Start small: **$1.00 USD** for your first test.
3. Tap **Charge $1.00**.

### 6.3 Pick the Lightning payment method

1. On the payment-method screen, scroll to or tap **Lightning** / **Bitcoin Lightning**.
   - If Lightning is missing, enable it in the Square Sandbox Dashboard under **Items & Orders → Payment Methods**, then sign out and back in.
2. Square generates a Lightning QR code on screen.

`[SCREENSHOT: Square POS displaying a Lightning bolt11 QR for $1.00]`

### 6.4 Scan it with WeaveWallet

1. On your other phone, open WeaveWallet.
2. Tap the big green **Scan to Pay** button.
3. Grant camera permission on first run.
4. Frame the Square QR.

Expected within ~1 second:

- Short haptic
- Camera closes
- **Confirm screen** appears with:
  - Recipient hash (matches the one Square encoded)
  - Amount in USD and in your selected asset
  - Memo (typically the Square order number / receipt id)

`[SCREENSHOT: Confirm screen showing the scanned Square invoice details]`

### 6.5 Authorize and pay

1. Verify the amount on the Confirm screen matches what Square is asking for.
2. (Optional) Tap the asset chip to switch between RUSD and USDI if both have capacity.
3. Tap **Pay**.
4. Authenticate with your passkey (Face ID / Touch ID / Windows Hello).
5. Watch the status panel cycle through:
   - **Creating Fiber invoice…**
   - **Sending payment on Fiber…**
   - **Fulfilling Lightning invoice…**
   - **Confirming Lightning settlement…**
6. Land on the **Success** screen within 3–8 seconds.

`[SCREENSHOT: Success screen with both legs marked settled]`

### 6.6 Verify on the Square side

On the Square POS, within a couple of seconds of the success screen:

- The charge screen flips to a **paid receipt** view ("Payment received")
- The order appears in **Sandbox Dashboard → Transactions** as `Completed` / `Lightning`
- If you have a Square Terminal in the loop, it prints/prompts for the
  customer receipt as it would for any other payment.

`[SCREENSHOT: Square POS showing the paid confirmation; dashboard showing the completed Lightning transaction]`

### 6.7 Verify on the wallet side

Back in WeaveWallet → tap **Activity** in the bottom nav (or scroll
the Home "Recent Activity" list and tap the new entry):

- Status: **Settled**
- Lightning sub-status: **Settled** (green) — the wallet only writes this label after independently confirming the Lightning leg with the node
- Amount: matches what Square charged
- Payment hash: **identical** to the one in Square's transaction detail
  (tap the entry → expand details to see it)

`[SCREENSHOT: WeaveWallet activity detail showing matching payment hash]`

### 6.8 Verify on the node side

```bash
docker compose exec fiber fnn-cli payment list --limit 1
```

Expected:
- `status: success`
- `amount` and `asset` match what you sent
- `fiber_tx_hash` matches the one shown in the wallet success screen

If all three sides (wallet, Square, node) report success **with
matching identifiers**, you have just completed a real, atomic,
two-leg cross-network payment. Congratulations.

## 7. Troubleshooting

Quick reference table — exact wallet error → most common cause →
fastest fix.

| Symptom in the wallet | Likely cause | Fix |
|---|---|---|
| **"Can't reach your Fiber node. Check that it's running and the URL is correct."** | RPC URL wrong, container down, firewall closed, DNS not resolving from the phone | See 7.1 |
| **"Your node rejected the auth token. Update it in Settings."** | Token in wallet ≠ token in `fiber.yaml`, or node not restarted after edit | See 7.2 |
| **"Your node took too long to respond. Try again in a moment."** | Node still indexing after cold start, or CKB peers starved | Wait 60s, retry; see 7.3 |
| **Wallet shows $0.00 but CLI shows funds** | Wrong asset selected, channel still confirming, or stale connection cache | See 7.4 |
| **"Not enough balance for this payment."** | Channel local balance < invoice amount | See 7.5 |
| **"Your node couldn't find a route to settle this payment."** | Bridge has no LN inbound liquidity, or wrong-network invoice | See 7.6 |
| **Activity row shows "Unverified" or "Pending confirmation" for the Lightning leg** | LN hop took longer than the wallet's poll window | See 7.7 |
| **"That doesn't look like a valid Lightning invoice."** | Scanned LNURL, on-chain BTC, or non-LN QR | See 7.8 |
| **Square never marks the order paid** | LN settled but Square's webhook didn't fire | See 7.9 |
| **Browser won't open camera** | HTTPS not active, or camera permission denied | See 7.10 |

---

### 7.1 "Can't reach your Fiber node. Check that it's running and the URL is correct."

```bash
# On the VPS / node host:
docker compose ps                    # expect: Up (healthy)
curl -s http://localhost:8227 -X POST \
  -H "Content-Type: application/json" \
  --data '{"jsonrpc":"2.0","id":1,"method":"node_info","params":[]}'
# Expect: JSON response with the node's pubkey
```

If the curl works locally but the wallet still can't reach it:

- Your phone is on a different network than the node. `localhost` from
  the phone is the phone, not your laptop.
- You're going through a reverse proxy that's stripping `Content-Type`
  or rejecting the JSON body. Check the proxy logs.
- DNS for `node.example.com` hasn't propagated to your phone's resolver
  yet. Test with `dig node.example.com` from the VPS.

### 7.2 "Your node rejected the auth token. Update it in Settings."

```bash
# Confirm the token actually in use:
docker compose exec fiber grep auth_token /root/.fiber/config/fiber.yaml
```

The string after `auth_token:` must match the wallet's Settings field
byte-for-byte. Watch for stray whitespace or smart-quote characters
from copy/paste. After editing, **restart** the node — Fiber reads the
config at startup only:

```bash
docker compose restart fiber
```

If you didn't set a token in config, the wallet field must be blank
(no spaces).

### 7.3 "Your node took too long to respond. Try again in a moment."

```bash
docker compose logs --tail=100 fiber | grep -iE "peer|indexer|sync"
```

- If `Connected to 0 peers`: open port 8228 in your firewall and wait.
- If `indexing`: let it finish — first cold start can take 5–10 minutes.
- If `RPC pool exhausted`: too many in-flight calls. Bounce the container.

### 7.4 Wallet shows zero balance but CLI shows funds

1. In WeaveWallet, tap the asset toggle (top-right of balance card)
   between RUSD and USDI — you may be looking at the wrong asset.
2. Settings → Test connection → Save (forces a fresh `list_channels`
   call and busts the client cache).
3. `fnn-cli channel list` — if all channels show `state: pending`,
   they haven't confirmed yet. Wait for confirmations.

### 7.5 "Not enough balance for this payment"

```bash
docker compose exec fiber fnn-cli channel list
```

Compare `local_balance` on each channel to the invoice amount. Fiber
won't split a payment across channels automatically. Either:

- Open a larger channel (`channel open --funding-amount ...`)
- Rebalance (swap from another asset, or have your bridge peer push)
- Pay a smaller invoice for the test

### 7.6 "Your node couldn't find a route"

Most often this is a Lightning-side problem, not a Fiber-side one.

```bash
docker compose logs --tail=200 fiber | grep -iE "htlc|route|bridge"
```

Look for `no_route`, `temporary_channel_failure`, or
`fee_insufficient`. Fixes:

- Ask your bridge peer to rebalance LN inbound
- Add a second bridge peer (multiple `lightning_bridges` entries)
- Confirm the invoice is on the same network as your bridge (testnet ↔ testnet)

### 7.7 Activity row shows "Pending confirmation" or "Unverified" for the Lightning leg

The Fiber side settled but the LN-side confirmation hasn't reached
your node yet. The wallet labels the Lightning sub-status one of:
**Settled** (green), **Pending confirmation** (amber), **Failed**
(amber), or **Unverified** (muted) — see the activity drawer.

1. WeaveWallet → Activity → tap the entry → tap **Re-check**.
   Most "Pending confirmation" rows flip to **Settled** within 30 seconds.
2. If a row stays **Unverified** for >10 minutes:
   ```bash
   docker compose logs --tail=500 fiber | grep <payment_hash>
   ```
   Look for the bridge's settlement HTLC. If the HTLC failed, your
   node owes a refund — check `fnn-cli payment refund-status <hash>`.

### 7.8 "That doesn't look like a valid Lightning invoice."

The scanner expects a bolt11 string (with or without a `lightning:`
prefix). It rejects:

- LNURL-pay (`lnurl1...` or `https://...` payloads)
- BIP21 bitcoin URIs (`bitcoin:...`)
- Plain BTC addresses
- LN node pubkeys / connection strings

If Square is showing an LNURL instead of a raw bolt11, switch the
Square POS payment method to **Lightning Invoice** (not "Lightning
Address") in **Sandbox Dashboard → Payment Methods**.

### 7.9 Square never marks the order paid (webhook not firing)

Square confirms Lightning payments via a webhook from their LN
provider. The wallet's success ≠ Square's success.

1. **Sandbox Dashboard → Webhooks** — confirm a subscription exists for
   `payment.updated` and is `Active`.
2. If you self-host a webhook receiver, confirm it's reachable from
   Square's IPs (test with the **Send test event** button).
3. Force-refresh the POS app — sometimes the local UI lags the backend
   by several seconds even though the order is marked paid server-side.
4. Check **Transactions** in the Sandbox Dashboard directly — if it
   shows `Completed`, the payment really did go through and only the
   POS UI is stale.

### 7.10 Browser won't open camera

- The wallet **must** be served over **HTTPS** (or `localhost`).
  `http://wallet.example.com` will fail silently. Confirm the address
  bar shows a lock icon.
- iOS Safari: Settings → Safari → Camera → set to **Ask** or **Allow**.
- Android Chrome: long-press the URL → Site Settings → Camera → Allow.
- Make sure the Caddy `Permissions-Policy` header from section 2.4 is
  in place — it explicitly allows `camera=(self)`.

## 8. Success criteria for a valid test

Tick all of these before claiming the deployment is ready:

- [ ] Wallet loads at `https://wallet.example.com` over HTTPS, no cert warning
- [ ] Passkey unlock succeeds on first registration and on subsequent visits
- [ ] Settings → Test connection returns green with the correct node alias
- [ ] Home balance card shows the same RUSD/USDI numbers as `fnn-cli wallet balance`
- [ ] **At least one happy-path payment** has completed end-to-end:
  - WeaveWallet Activity row shows the Fiber leg as **Settled** AND the Lightning sub-status as **Settled** (green)
  - Square POS shows the paid receipt
  - `fnn-cli payment list` shows `status: success`
  - **All three payment hashes match**
- [ ] At least **three failure cases** from [`testing-guide.md` section 6](./testing-guide.md#6-failure-cases-to-test) have been triggered and produced the documented friendly errors:
  - Low channel liquidity → "Not enough balance for this payment."
  - Node offline mid-payment → "Can't reach your Fiber node. Check that it's running and the URL is correct."
  - Phone in airplane mode → orange offline banner
- [ ] No payment has ever debited stablecoin balance without a matching `settled` (or a documented, in-progress refund) on the node side
- [ ] You've reproduced **step 6.1 through 6.8** against Square three consecutive times with no manual intervention

When every box is ticked, you're ready to consider running this same
flow on **mainnet** with real stablecoin and a non-Sandbox Square
location. Re-do the entire guide from scratch on the production
environment — do not promote a testnet config to mainnet by editing a
config flag.
